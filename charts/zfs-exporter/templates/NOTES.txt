Metrics:  http://{{ include "zfs-exporter.fullname" . }}.{{ .Release.Namespace }}.svc:{{ .Values.listenPort }}/metrics

On a first install, the exporter pods stay Pending for a few seconds with
"Insufficient {{ .Values.devicePlugin.resourceName }}". That is expected,
and not a fault. Helm creates both DaemonSets at the same time, and the
scheduler cannot place the exporter until the device plugin registers the
resource with the kubelet. The condition clears itself.

A pod that stays Pending means the plugin found no /dev/zfs on any node where
it runs:

  kubectl -n {{ include "zfs-exporter.devicePluginNamespace" . }} logs -l app.kubernetes.io/component=device-plugin

Check that the nodes can reach their pools. A pod on a node with no ZFS kernel
module stays Running and reports every collector as failed. It does not crash:

  kubectl -n {{ .Release.Namespace }} logs -l app.kubernetes.io/component=exporter --tail=20

  kubectl -n {{ .Release.Namespace }} exec ds/{{ include "zfs-exporter.fullname" . }} -- \
    /usr/local/bin/zfs_exporter --version

A healthy scrape reports zfs_scrape_collector_success{collector="pool"} 1.
Alert on that metric: the exporter answers 200 even if it read nothing.

If the image does not carry a node's OpenZFS branch, the logs name that branch
("zfs-shim: no bundled OpenZFS userland for host version ..."). Set
zfsUserlandVersion to replace the detection.
